# Payouts, COD remittance, and fee settings

## Proposed tables

All new monetary columns are integer PHP centavos. Foreign keys use restricted deletion for financial records. Timestamps and primary IDs are included on each new table.

| Table | Columns and constraints |
| --- | --- |
| `seller_payable_entries` | `shop_id`, signed `amount_cents`, `shipment_settlement_id` nullable unique, `settlement_adjustment_id` nullable unique, `created_at`. Exactly one source ID is required. Entries are immutable. |
| `seller_payouts` | `shop_id`, `status` (`unpaid`, `paid`, `cancelled`), `amount_cents`, `created_by`, nullable `paid_by`, `paid_at`, `payment_reference`, `cancelled_by`, `cancelled_at`, `cancellation_reason`, timestamps. Paid reference and date are required to mark paid. |
| `seller_payout_items` | `seller_payout_id`, `seller_payable_entry_id`, nullable unique `active_entry_id`, signed `amount_cents`. Active unpaid and paid items set `active_entry_id` to the entry ID. Cancellation clears it while preserving the historical item. A check constraint requires the active key to be null or equal to the entry ID. |
| `rider_cod_remittances` | `rider_profile_id`, positive `amount_cents`, `received_at`, `note`, `recorded_by`, nullable `voided_at`, `voided_by`, `void_reason`, timestamps. |
| `marketplace_settings` | Singleton `id`, `commission_bps` (0–10,000), `delivery_fee_cents` (0–100,000, PHP 1,000 maximum), `payout_hold_days` (0–90, default 7), `updated_by`, timestamps. Changes use existing `security_audit_events` through `AuditTrail`. |

Index `shop_id`, `rider_profile_id`, and status columns used by each ledger and queue, including composite `(shop_id, status)` and `(rider_profile_id, received_at)` indexes.

## Ledger and state transitions

- Each existing or newly created `shipment_settlements` row produces one positive payable entry for `seller_cents`. Each `settlement_adjustments` row produces one negative entry for `seller_debit_cents`. Existing settlements and adjustments stay immutable.
- A settlement credit is eligible when its shipment's recorded `delivered` event is at least `payout_hold_days` old and no item has an open return. Open means `pending`, `seller_approved`, `seller_declined`, or `approved`. `rejected` and `refunded` are closed. A shipment with no recorded delivery event remains ineligible and appears on an admin needs-review list. Refund debits are effective immediately, including while their source credit is still held, so the available balance can become negative. Display the signed sum of eligible unpaid entries as **available**, with the portion already in an unpaid batch identified separately, and display ineligible unpaid credits separately.
- An admin creates at most one unpaid batch per seller, including all eligible, unassigned entries and outstanding unpaid debits. Its signed sum must be positive. Verify that `seller_payouts.amount_cents` equals the sum of its items when creating it and again before marking it paid. Marking it paid records the reference, date and administrator. Before payment, recheck eligibility and reconcile new debits under the same locks. If eligibility or the batch total changed, reject payment and let the admin cancel and rebuild. Cancelling an unpaid batch requires a reason, sets `cancelled`, releases its items, and writes an audit event. A paid batch cannot be cancelled. Paid items retain their unique active entry key and cannot be batched twice.
- Lock rows in this global order: order rows, then the shop row, then payable entries in ascending ID order. Each path takes only the locks it needs. Existing paths that post settlements or refund debits retain the order lock and take the shop lock afterwards. Payout creation, cancellation and payment lock the shop and then entries; they do not lock orders, and read eligibility without order locks. Retry lock-taking transactions at most three times on deadlock.
- For SQLite, enforce one unpaid batch per seller with a partial unique index on `shop_id` where `status = 'unpaid'`, and use an `IMMEDIATE` write transaction. For MySQL, enforce it with the generated unpaid-shop column and unique index, plus shop lock and check. Concurrency tests use two independent connections to a temporary file-based SQLite database, never `:memory:`, or a real MySQL database. Assert that only one creation succeeds, no entry is duplicated, and retry sees the existing batch.
- A return opened between an eligibility check and payout commit does not block that payout. If the return is refunded, its subsequently posted debit reduces the seller's balance immediately; opening a return alone does not create a debit, and a rejected return creates none. This residual exposure requires operational reconciliation.
- Rider COD collected is the sum of each internal rider-assigned COD shipment's snapshotted merchandise subtotal plus allocated shipping, only where `cod_collected_at` is set. Exclude external courier and demo payments. Remitted is the sum of non-voided remittances. Still owed is collected minus remitted. Lock the rider profile and recalculate within the insert transaction, rejecting a nonpositive amount or one above the current balance. An admin may void a row with a reason and audit event in the same transaction. Void is a one-way state change, and remittance rows are never edited or deleted. Existing `rider_earnings` remains a separate delivery-pay ledger and is not deducted from cash owed.
- Admins edit settings and record before/after values in the same transaction. At checkout, read one locked settings version and snapshot the commission policy and delivery allocation onto the order and fulfillments. Existing orders and settlements keep their snapshots. A mobile quote must be revalidated if settings change before order placement.

## Rounding and verification

Parse decimal peso inputs as decimal strings and convert exactly to centavos. Calculate commission as `intdiv(goods_cents * commission_bps + 5000, 10000)`, rounding half up to the nearest centavo. Allocate a flat delivery fee across shipments using integer division, assigning remainder centavos in stable shipment order. Refund commission reversals use the existing cumulative rounding rule. Convert legacy decimal rider earnings and shipment amounts exactly at the boundary without rewriting history.

The configured local SQLite database contained **0 settlements, 0 adjustments, 0 rider earnings, and 0 internal COD collections** when checked on 15 November 2026, so it needs no financial-row backfill now. Other environments may contain historical data. Provide an idempotent one-off backfill command with a read-only `--dry-run` that reports eligible, already imported and unidentifiable source rows before applying. Backfill identifiable settlements and adjustments only. Do not invent historical payout or remittance records, and reconcile prior cash movements before enabling balances in an environment with existing activity.

Part B tests cover eligibility boundaries and open returns, the available balance dipping when a refund debit exists while its credit is held, seller ownership, payout cancellation and paid-state protection, item-sum checks at creation and payment, duplicate and concurrent batches, refunds before and after payout, remittance limits and voids, backfill dry runs and idempotency, historical fee snapshots, settings bounds, audit events, and access by the wrong role or owner.
